Fixes #10244

## Summary
This PR adds health information to application history output so users can determine which deployment revision is currently healthy when viewing history from the CLI/API output.

Today, `argocd app get <app> -o yaml` includes history entries without health status, which makes it difficult to identify the last healthy deployment after one or more failed syncs. This change enriches each history item with the health result captured for that deployment.

## What changed
- Extend application history entry data to include health status.
- Populate history health fields when creating deployment history records.
- Ensure CLI YAML/JSON output includes history health data.
- Keep behavior backward-compatible for existing consumers (new field is additive).

## Why this is needed
Operators rely on deployment history to answer:
- Which revision is currently serving healthy traffic?
- What was the health of each rollout attempt?

Without health in history, failed syncs can obscure which commit is actually live and healthy.

## Example output (simplified)
```yaml
status:
  history:
    - id: 12
      revision: abcdef1
      deployStartedAt: "2026-05-01T12:00:00Z"
      deployedAt: "2026-05-01T12:00:32Z"
      health:
        status: Healthy
```

## Testing
- Add/extend unit tests for history serialization and API output to verify `health.status` is present in history entries.
- Validate `argocd app get <app> -o yaml` includes the new history health field.
- Confirm no regressions in history ordering and existing status fields.

## Backward compatibility and risk
- Additive API/output change only.
- Existing clients that ignore unknown fields continue to work.
- Low-to-moderate risk around status marshaling and CLI rendering paths.
